## 사명

법제처 API를 활용하여 자치법규와 연결된 상위법령의 개정 여부를 자동으로 감지하고,
개정이 필요한 자치법규만 선별하여 담당자에게 알림으로써 검토 업무를 지원한다.

## 핵심 규칙

**개정대상 판별**: 상위법령의 공포일자가 자치법규(조례)의 공포일자보다 이후이면
해당 자치법규는 개정 검토 대상이다.

## 핵심 원칙

### 데이터

#### I. 데이터 무결성

법령과 조문의 변경 이력은 시스템의 핵심 자산이다.

- 한번 기록된 변경 이력은 삭제하지 않는다.
- 변경 감지는 결정론적 방법(해시 비교)으로 수행하며, 감지 결과는 재현 가능해야 한다.
- 원본 데이터와 파생 데이터(diff, AI 출력 등)를 모두 보존한다.

### 설계

#### II. 관심사 분리

각 계층은 자신의 책임만 수행한다.

- 표현(API), 비즈니스 로직(Service), 데이터(Model)를 명확히 분리한다.
- 계층 간 의존은 단방향(표현 → 로직 → 데이터)이어야 한다.
- 프론트엔드와 백엔드는 정의된 API 계약을 통해서만 통신한다.

#### III. 외부 의존 격리

외부 시스템(법제처 API, LLM API 등)과의 통신은 격리된 경계에서만 수행한다.

- 외부 API 클라이언트는 비즈니스 로직과 분리된 별도 모듈로 관리한다.
- 외부 데이터의 비정형 응답에 대한 정규화를 경계에서 처리한다.
- 외부 시스템 장애가 내부 기능 전체를 중단시키지 않도록 설계한다.

#### IV. 비차단 처리

사용자 요청을 차단하지 않는다.

- I/O 바운드 작업은 비동기로 처리한다.
- 장시간 작업(전체 법령 동기화, LLM 분석 등)은 백그라운드로 위임한다.
- API 응답 시간이 사용자 경험을 저해하지 않도록 한다.

#### V. 환경 재현성

누구든, 어디서든 동일한 개발 환경을 재현할 수 있어야 한다.

- 인프라 구성은 코드로 선언한다.
- 환경별 차이는 환경 변수로만 관리한다.
- 서비스 간 의존 순서와 상태 확인을 명시적으로 정의한다.

### 보안

#### VI. 보안 기본 적용

본 시스템은 관공서 보안성 검토 승인 대상이며, 시큐어코딩 가이드라인을 준수한다.

- 행정안전부 소프트웨어 개발보안 가이드(시큐어코딩)를 준수한다.
- 인증되지 않은 접근은 기본적으로 차단한다.
- 비밀 정보(비밀번호, 토큰, API 키)는 평문으로 저장하거나 전송하지 않는다.
- 보안 우회는 개발 환경에서만, 환경 변수를 통해서만 허용한다.
- 사용자 입력과 외부 데이터는 항상 검증 및 정화(sanitize)한다.
- 보안성 검토 승인에 필요한 취약점 점검 항목을 설계 단계부터 반영한다.

### 사용자 경험

#### VII. 사용자 중심 설계

시스템의 주 사용자는 지방자치단체 법규 담당 공무원이다.

- **사용자**: 소속 부서의 조례만 열람/검토할 수 있다. 개정 여부를 검토하여 결과를 저장하고, 최종적으로 개정 대상 또는 개정 제외 대상까지 관리한다.
- **관리자**: 모든 부서의 조례를 열람/검토할 수 있으며, 사용자의 검토 결과를 승인할 권한을 가진다. 법령 동기화, 조례-법령 연계 설정, 부서 및 사용자 관리 등 시스템 운영을 담당한다.
- UI와 메시지는 사용자의 언어(한국어)와 업무 용어를 사용한다.
- 역할별로 네비게이션 메뉴를 분리하여 해당 역할의 기능만 표시한다.
  프론트엔드(메뉴 노출)와 백엔드(API 접근 제어) 양쪽에서 권한을 강제한다.
- 인증 모델이 변경되더라도 역할 기반 접근 제어 원칙은 유지한다.

#### VIII. AI 보조 활용

LLM 등 AI 모델의 출력은 보조 도구이며, 최종 판단을 대체하지 않는다.

- AI 생성 결과는 **참고용**으로만 제공하며, 최종 의사결정은 담당자가 수행한다.
- AI 분석은 자동 실행하지 않으며, 담당자의 명시적 요청(버튼 클릭)으로만 수행한다.
- 동일 대상에 대한 AI 분석은 **1회만 수행**하며, 결과 확정 후 재실행하지 않는다.
  원하는 결과가 나올 때까지 반복 실행하는 것을 방지하여 감사 추적성을 보장한다.
- AI 생성 여부를 메타데이터에 기록하고, UI에서 "AI 생성" 라벨로 명확히 구분한다.
- LLM에 전송하는 데이터는 공개 정보(법령, 조례 텍스트)만 포함하며, 개인정보를 전송하지 않는다.
- LLM API 클라이언트는 III. 외부 의존 격리 원칙에 따라 별도 모듈로 관리한다.
- LLM API 장애가 기존 기능(수동 검토)을 중단시키지 않는다.
- AI 입력(프롬프트)과 출력(응답)을 모두 보존하여 I. 데이터 무결성 원칙을 준수한다.

## 전략 방향

### 시스템 전환

**Phase 1 (현재)**: Python/React로 기능 및 UI를 완성한다.
**Phase 2**: 완성된 시스템을 **자바 기반 전자정부표준프레임워크(eGovFrame)**로 전환한다.

Phase 1은 Phase 2의 설계 기준(프로토타입)이 된다. 따라서:

- 비즈니스 로직은 특정 프레임워크에 종속되지 않도록 설계한다.
- API 계약(엔드포인트, 요청/응답 스키마)은 전환 시 그대로 옮길 수 있도록 표준적으로 정의한다.
- 데이터베이스 스키마는 전환 대상 RDBMS와 호환되는 표준 SQL로 설계한다.
- UI 화면 구성과 사용자 흐름은 전환 후에도 동일하게 유지한다.

### 인증 모델 진화

인증 체계는 다음 단계로 진화한다. 각 단계의 구현 세부사항은
해당 기능의 Spec 문서에서 정의한다.

- **Auth Phase A (현재)**: 부서 단위 로그인. 개인 사용자 계정 없이
  부서 정보로 인증하며, 관리자는 별도 비밀번호로 접근한다.
- **Auth Phase B (추후)**: 개인별 로그인. 사용자 이름, 이메일 등
  개인 식별 정보를 기반으로 인증하며, 부서 소속은 사용자 속성으로 관리한다.

전환 시 준수 사항:

- Auth Phase A에서 축적된 데이터(검토 결과 등)는 Phase B로 이관 가능해야 한다.
- 인증 로직은 비즈니스 로직과 분리하여 인증 방식 변경이 다른 기능에 영향을 주지 않도록 한다.
- 역할(사용자/관리자)과 권한 체계는 인증 모델과 독립적으로 유지한다.

## 운영 규칙

### 기술 제약

- 동일 역할의 라이브러리를 중복 도입하지 않는다.
- 기술 스택 변경은 spec 또는 plan 문서에서 근거를 명시한 후 적용한다.
- 코드 리뷰 시 시큐어코딩 가이드라인, 성능(N+1 쿼리), 접근성을 확인한다.
- 보안성 검토 승인 기준에 부합하지 않는 코드는 머지하지 않는다.

### 거버넌스

이 Constitution은 프로젝트의 최상위 원칙 문서이며,
모든 설계 및 구현 결정에 우선한다.

- **개정 절차**: 변경 사유와 영향 범위를 문서화한 후 적용한다.
- **버전 관리**: MAJOR(원칙 삭제/재정의/구조 변경), MINOR(원칙 추가/확장), PATCH(문구 수정).
- **준수 검증**: plan 단계에서 Constitution Check를 수행한다.
- **세부 지침**: 기술 스택, 개발 워크플로우 등 구현 세부사항은 spec/plan 문서에서 관리한다.
