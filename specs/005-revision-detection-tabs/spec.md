# Feature Specification: 개정 검토 대상 판별 방식 병렬 탭

**Feature Branch**: `005-revision-detection-tabs`
**Created**: 2026-02-27
**Status**: Draft
**Constitution Ref**: Core Rule(개정대상 판별), II. 외부 의존 격리, VII. 사용자 중심 설계

## 개요

현재 시스템은 **공포일자 비교** 방식 하나로 개정 검토 대상을 판별한다.
이를 3가지 독립적 접근법으로 확장하여 **별도 탭으로 병렬 구축**한 뒤,
실무 평가를 통해 최적의 방식을 선택하고 나머지를 탈락시킨다.

## Clarifications

### Session 2026-03-01

- Q: 탭 C의 기본 데이터 소스를 JSON/XML 중 무엇으로 할지? → A: 탭 C 기본 소스는 JSON(`lawService.do?type=JSON`), XML은 실패 시 폴백
- Q: 제개정이유 기반 알림 발송 주기는 어떻게 할지? → A: 주 1회 요약 리포트 발송
- Q: 최종 방식 선택 후 비선택 탭 운영 정책은 어떻게 할지? → A: 비선택 탭은 읽기 전용 비활성화(제거하지 않음)
- Q: 주간 요약 리포트 제공 채널은 무엇으로 할지? → A: 시스템 내 인앱 알림함으로만 제공
- Q: 탭 C 검토 필요 판정 기준은 무엇으로 할지? → A: 매핑된 조문만 검토 필요, 비매핑은 참고(매핑 검토)

### 3가지 접근법

| 탭 | 방식 | 데이터 소스 | 현재 상태 |
|----|------|------------|-----------|
| **A. 법령비교** | 법령 공포일자 vs 조례 공포일자 비교 | `lawSearch.do?target=law` (JSON) | 기존 구현 완료 |
| **B. 조문비교** | 조문별 변경여부/제개정유형 추적 | `lawService.do?target=law` (JSON) - 조문단위 | 부분 구현 (ArticleList/Detail) |
| **C. 개정이유비교** | 개정문내용에서 변경 조문 자동 추출 + 제개정이유 분석 | `lawService.do?target=law` (JSON, 실패 시 XML 폴백) | **신규** |

## API 조사 결과 (2026-02-27)

### 핵심 발견: JSON 응답 구조

| 필드 | JSON 경로 | XML 태그 | 비고 |
|------|-----------|----------|------|
| 기본정보 | `법령.기본정보` | `<기본정보>` | 법령명, 공포일자 등 |
| 조문단위 | `법령.조문.조문단위[]` | `<조문단위>` | 제정/타법개정 시 포함 |
| 조문제개정유형 | `조문단위[].조문제개정유형` | `<조문제개정유형>` | 조문별 개정 유형 |
| 조문변경여부 | `조문단위[].조문변경여부` | `<조문변경여부>` | Y/N |
| **제개정이유내용** | **`법령.제개정이유.제개정이유내용`** | `<제개정이유내용>` | **list of list (문장 배열)** |
| **개정문내용** | **`법령.개정문.개정문내용`** | `<개정문내용>` | **list of list (줄 배열)** |

> **주의**: JSON에서 `법령.제개정이유내용`(1depth)은 None. `법령.제개정이유.제개정이유내용`(2depth)이 정확한 경로.

### JSON 제개정이유/개정문 데이터 구조

```json
{
  "법령": {
    "제개정이유": {
      "제개정이유내용": [["[일부개정]", "◇ 개정이유 및 주요내용", "내용..."]]
    },
    "개정문": {
      "개정문내용": [["⊙법률 제XXXXX호", "법률명 일부개정법률", "제X조...", ...]]
    }
  }
}
```

- 제개정이유내용: `list[list[str]]` - 외부 리스트는 단일 항목, 내부 리스트는 문장 배열
- 개정문내용: `list[list[str]]` - 외부 리스트는 단일 항목, 내부 리스트는 줄 단위 배열
- 텍스트 조합: `"\n".join(data[0])` 으로 전문 복원

### API 호출 방식

```
GET https://www.law.go.kr/DRF/lawService.do
    ?OC={API_KEY}
    &target=law
    &MST={법령일련번호}    (또는 &ID={법령ID})
    &type=JSON              ← JSON/XML 모두 가능
```

### 제개정이유내용 예시

```
[일부개정]

◇ 개정이유 및 주요내용

  전국 어디서든 소아ㆍ청소년환자가 신속하게 의료서비스를 받을 수 있도록
  119구급상황센터의 업무에 소아ㆍ청소년환자에 대한 상담ㆍ안내ㆍ지도 업무를 추가하고...

<법제처 제공>
```

### 개정문내용 예시 (변경 조문 자동 추출 가능)

```
119구조ㆍ구급에 관한 법률 일부를 다음과 같이 개정한다.

제10조의2제1항 중 "이송"을 "이송 등"으로 하고...
제22조의2의 제목 중 "수집"을 "수집 및 응급의료정보통신망의 이용"으로 하고...
```

→ 정규식 `제(\d+조(?:의\d+)?)` 로 **변경된 조문번호 자동 추출 가능**
→ 위 예시에서 추출: `제10조의2`, `제22조의2`

### 주의사항

- **일부개정 MST**로 조회 시 `조문단위`가 0건 (개정 부분만 반환됨)
- 현행 전체 조문 목록은 현행법 MST로 별도 조회 필요
- 타법개정/제정 MST는 조문단위 포함

## User Scenarios & Testing

### User Story 1 - 탭 A: 법령비교 (Priority: P1)

담당자가 조례의 상위법령 공포일자와 조례 공포일자를 비교하여 개정 검토가 필요한지 확인한다.

**Why this priority**: 현재 구현된 Core Rule. 가장 단순하고 빠른 판별 방법.

**Independent Test**: 조례 상세 → 개정검토 탭 → 법령비교 서브탭 → 개정 필요 법령 표시

**Acceptance Scenarios**:

1. **Given** 상위법령의 공포일자가 조례의 공포일자보다 이후,
   **When** 법령비교 서브탭 확인,
   **Then** "개정 검토 필요" 표시, 공포일자 차이(일수) 표시
2. **Given** 상위법령의 공포일자가 조례의 공포일자 이전,
   **When** 법령비교 서브탭 확인,
   **Then** "최신 상태" 표시
3. **Given** 여러 상위법령이 연결된 조례,
   **When** 법령비교 서브탭 확인,
   **Then** 각 법령별로 개정 필요 여부 표시, 가장 최근 개정 법령 상단 정렬

---

### User Story 2 - 탭 B: 조문비교 (Priority: P1)

담당자가 상위법령의 개별 조문별 변경 여부와 제개정 유형을 확인하여 정밀하게 개정 검토 대상을 파악한다.

**Why this priority**: 조문 단위 추적으로 공포일자 방식보다 정밀한 판별 가능.

**Independent Test**: 조례 상세 → 개정검토 탭 → 조문비교 서브탭 → 변경된 조문 목록 표시

**Acceptance Scenarios**:

1. **Given** 상위법령의 조문 중 조문변경여부가 Y인 조문이 있을 때,
   **When** 조문비교 서브탭 확인,
   **Then** 변경된 조문 목록 (조문번호, 제개정유형, 변경여부) 표시
2. **Given** 조례에 매핑된 조문 중 변경된 것이 있을 때,
   **When** 조문비교 서브탭 확인,
   **Then** "매핑 조문 변경 감지" 강조 표시
3. **Given** 조문제개정유형이 "신설"인 조문,
   **When** 조문비교 서브탭 확인,
   **Then** 신설 조문 별도 섹션으로 표시 (신규 매핑 검토 필요)

---

### User Story 3 - 탭 C: 개정이유비교 (Priority: P1) ★ 신규

담당자가 법제처 API의 제개정이유내용과 개정문내용을 조회하여,
개정된 조문 목록을 자동 추출하고 조문개정 검토대상을 분류한다.

**Why this priority**: 개정문내용에서 변경 조문을 자동 파싱하여 검토대상 자동 분류 가능. 공포일자/조문변경 방식과 교차 검증 가치.

**Independent Test**: 조례 상세 → 개정검토 탭 → 개정이유비교 서브탭 → 제개정이유 표시 + 변경 조문 자동 추출

**Acceptance Scenarios**:

1. **Given** 상위법령의 MST로 JSON API 호출(실패 시 XML 폴백),
   **When** 개정이유비교 서브탭 확인,
   **Then** 기본적으로 JSON API로 제개정이유내용 전문 표시, JSON 실패 시 XML 폴백으로 표시 (개정이유 및 주요내용)
2. **Given** 개정문내용이 존재하는 법령,
   **When** 개정이유비교 서브탭에서 "변경 조문 자동 추출" 실행,
   **Then** 개정문내용에서 `제X조(의X)` 패턴을 파싱하여 변경된 조문번호 목록 표시
3. **Given** 자동 추출된 조문번호 목록,
   **When** 조례에 매핑된 조문과 비교,
   **Then** 매핑된 조문 중 변경된 것 = "검토 필요", 비매핑 신규 = "매핑 검토 추천"
4. **Given** 타법개정(제개정이유가 간소한 경우),
   **When** 개정이유비교 서브탭 확인,
   **Then** 제개정이유가 없거나 짧으면 "타법개정 - 상세 확인 필요" 안내

---

### User Story 4 - 서브탭 비교 및 최종 선택 (Priority: P2)

관리자가 3가지 서브탭(법령비교/조문비교/개정이유비교)의 판별 결과를 비교하여 가장 효과적인 방식을 평가한다.

**Why this priority**: 병렬 구축 후 실무 평가로 최적 방식 선택.

**Independent Test**: 동일 조례에 대해 3개 서브탭 결과 비교 → 일치/불일치 분석

**Acceptance Scenarios**:

1. **Given** 3개 서브탭이 모두 구현된 상태,
   **When** 관리자가 "서브탭 비교" 뷰 진입,
   **Then** 동일 조례에 대한 3개 서브탭 판별 결과를 나란히 비교
2. **Given** 법령비교는 "개정 필요"이나 조문비교는 "변경 없음"인 경우,
   **When** 비교 확인,
   **Then** 불일치 원인 분석 (예: 부칙만 변경, 관련 없는 조문만 변경)
3. **Given** 평가 완료 후,
   **When** 관리자가 최종 방식 선택,
   **Then** 선택된 서브탭을 기본 뷰로 설정하고, 나머지 서브탭은 읽기 전용 비활성화 상태로 유지한다

---

### User Story 5 - 제개정이유 기반 주간 요약 리포트 발송 (Priority: P2)

시스템이 제개정이유 분석 결과를 기반으로 담당 부서에 개정 검토 요약 리포트를 주 1회 자동 발송한다.

**Why this priority**: 개정 감지 후 담당자 알림까지 자동화하여 업무 효율 극대화.

**Independent Test**: 한 주 동안 감지 건 누적 → 제개정이유 분석 결과 집계 → 해당 부서에 주간 요약 리포트 발송

**Acceptance Scenarios**:

1. **Given** 한 주 동안 신규 법령 개정이 감지되고 제개정이유 분석이 완료된 상태에서,
   **When** 주간 발송 시점이 도래하면,
   **Then** 해당 주의 검토대상 건을 묶어 담당 부서의 시스템 내 인앱 알림함에 주간 요약 리포트를 생성한다
2. **Given** 주간 요약 리포트 내용,
   **When** 담당자가 리포트를 확인하면,
   **Then** 제개정이유 요약, 변경 조문 목록, 영향받는 조례 목록이 포함된다
3. **Given** 담당자가 검토 완료 후,
   **When** 검토 결과 입력,
   **Then** 검토 이력에 기록

---

### Edge Cases

- JSON API 호출 실패 시 XML 폴백 또는 에러 처리
- 개정문내용이 매우 긴 경우(대규모 법률) 파싱 성능
- 제개정이유내용이 없는 법령 (오래된 법령, 제정 법령 등)
- 개정문내용의 조문번호 패턴이 비정형인 경우 (예: "별표 1", "서식")
- 일부개정 MST vs 현행법 MST 구분 처리
- 동일 법령의 여러 개정 이력을 시간순으로 추적

## Requirements

### Functional Requirements

- **FR-001**: `lawService.do?target=law&type=JSON` API를 호출하여 `법령.제개정이유.제개정이유내용`과 `법령.개정문.개정문내용`을 조회한다
- **FR-002**: 개정문내용에서 `제(\d+조(?:의\d+)?)` 패턴으로 변경된 조문번호를 자동 추출한다
- **FR-003**: 추출된 조문번호를 조례-조문 매핑(`ordinance_article_mappings`)과 대조하여 검토대상을 분류한다
- **FR-004**: 3가지 판별 방식(공포일자/조문변경/제개정이유)을 별도 탭으로 제공한다
- **FR-005**: 각 탭은 독립적으로 동작하며, 다른 탭의 데이터에 의존하지 않는다
- **FR-006**: XML API 응답의 CDATA 섹션을 정리하여 깨끗한 텍스트로 표시한다
- **FR-007**: 제개정이유 분석 결과를 기반으로 담당 부서에 주 1회 검토 요약 리포트를 생성/발송할 수 있다
- **FR-008**: 관리자가 3탭 비교 뷰에서 판별 결과의 일치/불일치를 확인할 수 있다
- **FR-009**: 최종 방식 선택 후 비선택 탭은 삭제하지 않고 읽기 전용 비활성화 상태로 유지해야 한다
- **FR-010**: 주간 요약 리포트는 이메일/외부 메시지 없이 시스템 내 인앱 알림함으로만 제공해야 한다
- **FR-011**: 탭 C에서 자동 추출된 조문 중 조례에 매핑된 조문만 "검토 필요"로 분류하고, 비매핑 조문은 "참고(매핑 검토)"로 분류해야 한다

### Technical Requirements

- **TR-001**: 기존 `MolegClient.get_law_detail()`에 제개정이유/개정문 파싱을 추가한다 (JSON 경로: `법령.제개정이유.제개정이유내용`, `법령.개정문.개정문내용`)
- **TR-002**: JSON `list[list[str]]` 구조를 `"\n".join(data[0])`으로 텍스트 변환한다
- **TR-003**: 제개정이유/개정문 데이터는 DB에 캐싱하여 반복 API 호출을 방지한다
- **TR-004**: 프론트엔드 탭은 Ant Design `<Tabs>` 컴포넌트로 구현한다
- **TR-005**: 각 탭의 API 호출은 lazy loading (탭 클릭 시 최초 1회 조회)

### Key Entities (신규/변경)

- **LawRevisionReason** (신규): 법령 제개정이유. law_mst, revision_reason_content, amendment_content, extracted_articles (JSON), fetched_at
- **RevisionDetectionResult** (신규): 판별 결과. ordinance_id, law_id, detection_method (A/B/C), needs_revision, detail (JSON)

### Data Flow

```
[법제처 JSON API (실패 시 XML 폴백)] → 제개정이유내용 + 개정문내용
                    ↓
              [개정문 파서] → 변경 조문번호 추출 (제X조, 제X조의X)
                    ↓
         [매핑 대조] → ordinance_article_mappings와 비교
                    ↓
         [검토대상 분류] → 검토필요 / 변경없음 / 신규매핑추천
                    ↓
         [주간 리포트 생성] → 담당 부서 통보
```
