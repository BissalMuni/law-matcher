# Feature Specification: LLM 기반 검토의견 자동 생성

**Feature Branch**: `006-llm-review-assistant`
**Created**: 2026-02-28
**Status**: Draft
**Input**: User description: "법령 제개정이유와 조례를 LLM API에 전송하여 개정내용 요약 및 검토의견 초안을 자동 생성하는 기능"
**Constitution Ref**: I. 데이터 무결성, III. 외부 의존 격리, VI. 보안 기본 적용, VII. 사용자 중심 설계, VIII. AI 보조 활용

## 개요

법령 동기화 후 감지된 개정 법령의 **제개정이유내용**과 **개정문내용**을 해당 조례와 함께
LLM API에 전송하여:

1. **개정내용 요약**: 법령 개정의 핵심 변경사항을 한국어로 요약
2. **검토의견 초안**: 해당 조례의 개정 필요 여부에 대한 의견 초안을 자동 생성

담당자는 LLM이 생성한 초안을 참고하여 최종 검토의견을 작성한다.
LLM 결과는 **참고용(보조)**이며, 최종 판단은 반드시 담당자가 수행한다.

### LLM 프로바이더

시스템은 다중 LLM 프로바이더를 지원하며, **DB 기반 관리**와 프로바이더 추상화 레이어를 통해 운영한다:

- **지원 프로바이더**: Claude (Anthropic), ChatGPT (OpenAI), Gemini (Google)
- **프로바이더/모델 관리**: `llm_providers` DB 테이블에서 프로바이더명, 모델명, 활성 상태 등을 관리한다. **관리자 전용 설정 탭**에서 프로바이더 추가/수정/활성화 전환이 가능하다
- **추상화 구조**: 공통 인터페이스(`LlmClient`)를 정의하고, 각 프로바이더별 어댑터를 구현
- **API 키 관리**: 프로바이더별 환경변수 (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_AI_API_KEY`). API 키는 보안상 환경변수로만 관리하며, DB에 저장하지 않는다
- **모델 선택**: 관리자가 DB에서 프로바이더별 모델명을 설정. 미설정 시 프로바이더별 기본 모델 사용

### AI 분석 호출 구조

AI 분석은 **1회 통합 호출**로 요약과 검토의견 초안을 동시에 생성한다 (Constitution VIII "1회만 수행" 준수):

- **"AI 분석" 버튼 1회 클릭** → LLM이 제개정이유+개정문+조례 정보를 분석하여:
  - ① **개정내용 요약**: 핵심 변경사항, 변경 조문 목록, 조례 영향
  - ② **검토의견 초안**: 검토 결과(개정필요/개정불필요) + 의견 내용
- 요약은 **개정검토 탭**에 표시, 초안은 **검토의견 작성 모달**에서 자동 채움
- 1회 호출로 두 결과를 동시 생성하므로 Constitution VIII 원칙에 부합

### LLM 처리 방식

**동기 처리** + 로딩 UI 표시:

- "AI 분석" 버튼 클릭 → 로딩 스피너 표시 → LLM 응답 수신 → 결과 표시
- 타임아웃 30초 (FR-010). 타임아웃 시 에러 안내

### 프롬프트 관리

LLM에 전송하는 프롬프트 템플릿은 **YAML/JSON 설정 파일**로 관리한다:

- 프롬프트 템플릿 파일: `backend/config/prompts.yaml`
- 코드 변경 없이 프롬프트 수정 가능 (배포는 필요)
- 프롬프트 내 변수: `{law_name}`, `{revision_reason}`, `{amendment_content}`, `{ordinance_name}`, `{ordinance_text}` 등
- LLM 응답 형식: **JSON 구조화 출력 강제**. 파싱 실패 시 1회 재시도, 2회 실패 시 에러 처리

### 토큰 제한 초과 처리

입력 텍스트가 LLM 토큰 제한을 초과하는 경우 **2단계 처리**:

1. **1차 호출**: 긴 텍스트를 LLM에 요약 요청
2. **2차 호출**: 요약된 내용을 기반으로 분석(요약+초안) 수행
- 토큰 초과 여부는 입력 텍스트 길이로 사전 판단

### Rate Limiting

시스템 전체에 **분당 최대 N회** LLM 호출 제한을 적용한다:

- 제한 초과 시 요청을 큐에 대기시키고 "AI 분석 대기 중 (N번째)" 안내
- 관리자 설정 탭에서 제한값 조정 가능

### 상위법령 복수 연결 시 AI 분석

조례에 상위법령이 복수 연결된 경우, **법령별로 개별 AI 분석을 수행**한다:

- 각 법령-조례 조합에 대해 별도의 AI 요약 및 검토의견 초안 생성
- `LlmAnalysisResult`는 `(ordinance_id, law_id)` 단위로 저장
- UI에서는 법령별로 AI 분석 결과를 구분하여 표시

## User Scenarios & Testing

### User Story 1 - AI 통합 분석 (요약 + 검토의견 초안) (Priority: P1)

부서 담당자가 개정 검토 대상 조례의 상세 페이지에서 **"AI 분석" 버튼을 1회 클릭**하면,
LLM이 연결된 상위법령의 제개정이유와 개정문내용을 조례와 함께 분석하여
**개정내용 요약**과 **검토의견 초안**을 동시에 생성한다.

**Why this priority**: 법령 제개정이유 원문은 길고 복잡하여 핵심 파악이 어려움. 요약으로 검토 효율을 높이고, 동시에 검토의견 초안을 생성하여 의견 작성 진입장벽을 낮춘다.

**Independent Test**: 조례 상세 → AI 분석 버튼 → 요약 표시 + 검토의견 작성 시 초안 자동 채움

**Acceptance Scenarios**:

1. **Given** 개정 검토 대상 조례의 개정검토 탭에서,
   **When** "AI 분석" 버튼을 클릭하면,
   **Then** LLM이 1회 호출로 ① 개정내용 요약(주요 변경사항, 변경 조문 목록, 조례 영향)과 ② 검토의견 초안(결과: 개정필요/개정불필요, 의견 내용)을 동시에 생성한다
2. **Given** AI 분석이 완료된 후,
   **When** 개정검토 탭에서 요약을 확인하면,
   **Then** 주요 변경사항, 변경된 조문 목록, 조례에 미치는 영향이 구조화되어 표시되며 "AI 생성" 라벨이 붙는다
3. **Given** AI 분석이 완료된 후,
   **When** 검토의견 작성 모달을 열면,
   **Then** AI가 생성한 초안(결과+의견)이 입력 필드에 자동 채워지며, 담당자가 수정/보완 후 제출할 수 있다
4. **Given** 담당자가 AI 초안을 수정 없이 그대로 제출하면,
   **Then** AI 생성 여부가 메타데이터에 기록된다 (`is_ai_generated=true`, `ai_modified=false`)
5. **Given** LLM API 호출이 실패하면,
   **When** 에러 발생 시,
   **Then** "AI 분석을 수행할 수 없습니다. 직접 검토해 주세요" 안내 메시지 표시, 수동 검토의견 작성은 정상 동작
6. **Given** 입력 텍스트가 토큰 제한을 초과하면,
   **When** AI 분석 요청 시,
   **Then** 1차 요약 LLM 호출 → 2차 분석 LLM 호출의 2단계로 자동 처리되며, 사용자에게는 단일 결과로 표시된다

### User Story 3 - AI 결과 보존 및 재조회 (Priority: P2)

동일 법령-조례 조합에 대한 AI 분석 결과를 DB에 보존하고, 재조회 시 저장된 결과를 반환한다.
AI 분석은 1회만 수행되며, 결과 확정 후 재실행할 수 없다 (Constitution VIII 준수).

**Why this priority**: 1회 실행 원칙 보장 + LLM API 비용 절감 + 감사 추적성 확보.

**Independent Test**: 최초 요청 → LLM 호출 → 결과 저장 → 재조회 시 저장된 결과 반환 → AI 요약 버튼 비활성화

**Acceptance Scenarios**:

1. **Given** 동일 법령-조례 조합에 대해 AI 분석이 이미 완료된 경우,
   **When** 해당 조례 상세 페이지에 접근하면,
   **Then** 저장된 AI 분석 결과(요약+초안)를 즉시 표시하고, "AI 분석" 버튼은 비활성화된다
2. **Given** 법령이 새로 동기화되어 제개정이유가 변경된 경우 (공포일자 기준으로 새 버전 판별),
   **When** 해당 조례 상세 페이지에 접근하면,
   **Then** 기존 결과는 이력으로 보존하고, 새 법령 버전에 대해 AI 분석을 1회 수행할 수 있다

### User Story 3 - AI 분석 이력 조회 (Priority: P3)

관리자가 AI가 생성한 요약 및 검토의견 초안의 이력을 조회하여 활용도를 파악한다.

**Why this priority**: AI 활용 현황 모니터링 및 품질 평가에 필요.

**Independent Test**: 관리자 → AI 분석 이력 → 생성 건수, 채택률 확인

**Acceptance Scenarios**:

1. **Given** 관리자가 AI 분석 이력 페이지에 접근하면,
   **When** 기간별 필터를 적용하면,
   **Then** AI 분석 생성 건수, 초안 채택률(수정 없이 제출 비율), 프로바이더/모델별 사용 현황 표시

---

### User Story 4 - LLM 프로바이더/모델 관리 (Priority: P2)

관리자가 관리자 전용 설정 탭에서 LLM 프로바이더 및 모델 정보를 관리한다.

**Why this priority**: 프로바이더/모델 변경, 활성화 전환을 운영 중 수행할 수 있어야 한다.

**Independent Test**: 관리자 → 설정 → LLM 관리 탭 → 프로바이더 추가/모델 변경/활성 전환

**Acceptance Scenarios**:

1. **Given** 관리자가 LLM 관리 설정 탭에 접근하면,
   **When** 프로바이더 목록을 확인하면,
   **Then** 등록된 프로바이더명, 모델명, 활성 상태, API 키 설정 여부(마스킹)가 표시된다
2. **Given** 관리자가 프로바이더의 모델명을 변경하면,
   **When** 저장 후 AI 분석을 실행하면,
   **Then** 변경된 모델로 LLM 호출이 수행된다
3. **Given** 관리자가 활성 프로바이더를 전환하면,
   **When** 전환 후 AI 분석을 실행하면,
   **Then** 새 프로바이더로 호출되고, 기존 분석 결과는 이전 프로바이더의 model_name으로 보존된다

### Edge Cases

- LLM API 응답 지연(30초 초과) → 타임아웃 에러 처리, "AI 분석 시간이 초과되었습니다. 다시 시도해 주세요" 안내
- 제개정이유내용이 없는 법령(오래된 법령, 제정 법령) → "제개정이유 데이터가 없어 AI 분석을 수행할 수 없습니다"
- 매우 긴 제개정이유(토큰 제한 초과) → 1차 요약 LLM 호출 후 2차 분석 호출 (2단계 처리)
- LLM이 구조화 출력(JSON)을 반환하지 않는 경우 → 1회 재시도, 2회 실패 시 에러 처리
- 동시에 여러 건의 AI 분석 요청 → 시스템 전체 분당 N회 제한, 초과 시 큐 대기
- LLM API 키 만료/잔액 부족 → 관리자에게 알림
- AI 분석 중 네트워크 오류로 실패 → 실패 상태(`failed`) 기록, 해당 건에 한해 재시도 1회 허용 (성공 후 재실행 불가 원칙 적용)
- 이미 AI 분석 완료된 건에서 "AI 분석" 버튼 클릭 시도 → 버튼 비활성화로 원천 차단
- 설정된 LLM 프로바이더의 API 키가 없을 때 → "LLM API 키가 설정되지 않았습니다" 안내
- 프로바이더 전환 후 기존 분석 결과 → 그대로 유지 (model_name으로 어떤 프로바이더가 생성했는지 추적)
- 상위법령이 복수(N개) 연결된 조례 → 법령별 개별 AI 분석, UI에서 법령별 결과 구분
- 동일 법령의 새 버전(공포일자 변경) 감지 시 → 기존 결과는 이력 보존, 새 버전에 대해 1회 분석 허용

## Requirements

### Functional Requirements

**AI 분석 (통합 호출)**

- **FR-001**: "AI 분석" 버튼 1회 클릭으로 개정내용 요약과 검토의견 초안을 **동시에** 생성해야 한다 (1회 통합 호출)
- **FR-002**: 개정내용 요약은 개정검토 탭에, 검토의견 초안은 검토의견 작성 모달에 각각 표시/채움해야 한다
- **FR-003**: LLM 결과는 "AI 생성" 라벨로 명확히 구분하고, 담당자의 최종 판단을 대체하지 않음을 안내해야 한다
- **FR-004**: AI 생성 검토의견에는 메타데이터(`is_ai_generated`, `ai_modified`, `ai_model`, `ai_generated_at`)를 기록해야 한다
- **FR-005**: 동일 법령-조례 조합에 대한 AI 분석은 1회만 수행하며, 결과를 DB에 보존한다. 결과 확정 후 동일 대상에 대해 재실행할 수 없다 (Constitution VIII 준수). 상위법령이 복수 연결된 조례는 각 법령별로 개별 분석을 수행한다
- **FR-005a**: 법령이 새로 동기화되어 공포일자가 변경된 경우, 기존 결과는 이력으로 보존하고 새 법령 버전에 대해 1회 분석을 허용한다
- **FR-006**: LLM API 장애 시 기존 기능(수동 검토의견 작성)에 영향을 주지 않아야 한다

**LLM 프로바이더/모델 관리**

- **FR-007**: LLM API 키는 프로바이더별 환경변수(`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_AI_API_KEY`)로 관리하며, 코드에 하드코딩하지 않아야 한다. API 키는 보안상 DB에 저장하지 않는다
- **FR-007a**: 시스템은 Claude, ChatGPT, Gemini 세 가지 LLM 프로바이더를 지원하며, 공통 인터페이스(`LlmClient`)를 통한 프로바이더 추상화 레이어를 제공해야 한다
- **FR-007b**: 프로바이더별 모델명, 활성 상태 등을 `llm_providers` DB 테이블에서 관리해야 한다. 관리자가 설정 탭에서 모델 변경 및 활성 프로바이더 전환이 가능해야 한다
- **FR-007c**: 관리자 전용 "LLM 설정" 탭을 제공하여 프로바이더 목록 조회, 모델명 변경, 활성화 전환, API 키 설정 여부 확인(마스킹)이 가능해야 한다
- **FR-007d**: 관리자가 시스템 전체 Rate Limit(분당 최대 호출 수)을 LLM 설정 탭에서 조정할 수 있어야 한다

**보안 및 처리**

- **FR-008**: LLM에 전송하는 데이터는 법령/조례의 공개 정보만 포함해야 한다 (개인정보 제외)
- **FR-009**: AI 분석 요청은 인증된 사용자만 가능해야 한다
- **FR-010**: LLM API 호출 시 타임아웃(30초)과 재시도(최대 2회)를 적용해야 한다. "재시도"는 API 레벨의 투명한 재시도이며, 비즈니스 레벨의 "1회 수행" 원칙(FR-005)과는 별개이다
- **FR-011**: AI 분석은 자동 실행하지 않으며, 담당자의 명시적 요청(버튼 클릭)으로만 수행해야 한다
- **FR-012**: AI 분석이 완료된 대상은 해당 버튼을 비활성화하여 재실행을 방지해야 한다

**비차단 처리 (Constitution IV 준수)**

- **FR-013**: AI 분석은 동기 처리하며, 로딩 UI(스피너)를 표시하여 사용자에게 처리 중임을 안내해야 한다
- **FR-014**: 입력 텍스트가 토큰 제한을 초과하는 경우, 1차 요약 LLM 호출 → 2차 분석 LLM 호출의 2단계로 자동 처리해야 한다

**프롬프트 관리**

- **FR-015**: LLM 프롬프트 템플릿은 YAML/JSON 설정 파일(`backend/config/prompts.yaml`)로 관리해야 한다. 코드 변경 없이 프롬프트 수정이 가능해야 한다 (배포는 필요)

**응답 검증**

- **FR-016**: LLM 응답은 JSON 구조화 출력을 강제해야 한다. 파싱 실패 시 1회 재시도하고, 2회 실패 시 에러로 처리해야 한다

**Rate Limiting**

- **FR-017**: 시스템 전체에 분당 최대 N회 LLM 호출 제한을 적용해야 한다. 제한 초과 시 요청을 큐에 대기시키고 대기 상태를 사용자에게 안내해야 한다

### Key Entities

- **LlmAnalysisResult** (신규): LLM 분석 결과. ordinance_id, law_id, law_proclaimed_date (법령 버전 구분), status (pending/success/failed), input_hash (제개정이유+개정문+조례 텍스트의 해시), prompt, summary_text (요약), review_draft_text (초안), review_draft_result (개정필요/개정불필요), model_name, provider_name, token_usage, error_message, created_at
- **LlmProvider** (신규): LLM 프로바이더 관리. provider_name (claude/chatgpt/gemini), model_name, api_key_env_name, is_active, rate_limit_per_minute, created_at, updated_at
- **OrdinanceReview** (수정): `is_ai_generated`, `ai_modified` 필드 추가

## Success Criteria

### Measurable Outcomes

- **SC-001**: AI 요약 생성 응답 시간 10초 이내 (최초 생성 시)
- **SC-002**: AI 요약 재조회 응답 시간 1초 이내 (저장된 결과 반환 시)
- **SC-003**: AI 검토의견 초안 채택률(수정 없이 제출) 30% 이상
- **SC-004**: LLM API 장애 시 기존 기능 정상 동작 100%
- **SC-005**: 담당자의 검토의견 작성 시간 50% 단축 (AI 초안 활용 시)

## Clarifications

### Session 2026-02-28

- Q: 어떤 LLM 프로바이더를 지원하는가? → A: **Claude, ChatGPT, Gemini** 세 가지 모두 지원. 프로바이더 추상화 레이어(`LlmClient` 인터페이스)로 관리하며, 환경변수 `LLM_PROVIDER`로 선택
- Q: 상위법령이 복수 연결된 조례의 AI 분석 범위는? → A: **법령별 개별 분석**. 각 법령-조례 조합에 대해 별도 AI 호출 수행. `LlmAnalysisResult`는 `(ordinance_id, law_id)` 단위로 저장

### Session 2026-03-02

- Q: LLM 호출 처리 방식은? → A: **동기 처리 + 로딩 UI**. 30초 타임아웃. 백그라운드 처리 불필요
- Q: LLM 프롬프트를 어떻게 관리할까? → A: **YAML/JSON 설정 파일** (`backend/config/prompts.yaml`). 코드 변경 없이 수정 가능, 배포는 필요
- Q: 프로바이더별 모델 선택을 어떻게 할까? → A: **DB 테이블(`llm_providers`)로 관리** + **관리자 전용 LLM 설정 탭**에서 모델 변경/활성화 전환 가능
- Q: AI 요약과 AI 초안을 별도 기능으로 할까, 통합할까? → A: **1회 통합 호출**. "AI 분석" 버튼 1회 클릭으로 요약+초안을 동시 생성. Constitution VIII "1회만 수행" 원칙에 가장 부합
- Q: 토큰 제한 초과 시 처리는? → A: **요약 후 전송** (2단계). 1차 LLM 호출로 긴 텍스트 요약 → 2차 호출로 분석 수행
- Q: Rate Limiting 방식은? → A: **시스템 전체 분당 N회 제한**. 초과 시 큐 대기. 관리자 설정 탭에서 제한값 조정 가능
- Q: LLM 응답 검증은? → A: **구조화 출력(JSON) 강제**. 파싱 실패 시 1회 재시도, 2회 실패 시 에러 처리
- Q: input_hash의 범위는? → A: **입력 데이터만 해시** (제개정이유 + 개정문 + 조례 텍스트). 프롬프트 변경 시 재분석 허용
- Q: 법령 버전 추적(FR-005a)은? → A: **공포일자 기준**. 법령의 공포일자가 변경되면 새 버전으로 판별하여 재분석 허용
- Q: 005 탭 C 명칭은? → A: **"개정이유비교" → "개정이유분석"** 으로 변경
