# Feature Specification: 개정법령 변경이력 관리

**Feature Branch**: `001-law-change-tracking`
**Created**: 2026-02-27
**Status**: Draft
**Input**: User description: "개정법령 변경이력 관리 - 상위법령 동기화 후 변경사항 감지, 승인/반려 워크플로우, 일괄처리, Excel 내보내기"

## Clarifications

### Session 2026-02-27

- Q: law_changes 테이블의 역할은? → A: 동기화 감지 기록 전용. law_changes에 대한 승인/반려 워크플로우 없음
- Q: 빨간불(검토대상) 부여 기준은? → A: 시스템이 자동 판별하여 검토대상인 조례에만 부여 (전체 변경에 일괄 부여하지 않음)
- Q: "검토중" 상태 전환 방식은? → A: 부서 담당자가 조례 상세 페이지를 열람하면 자동으로 "검토대기"→"검토중" 전환
- Q: 검토의견 결과 항목은? → A: 개정필요 / 개정불필요 (2가지만). "검토중"과 "보류"는 검토의견 결과가 아니라 조례 상태임
- Q: 검토의견 승인 후 데이터 처리는? → A: 개정필요 승인→빨간불 유지(개정확정), 개정불필요 승인→빨간불 해제, 반려→검토대기로 원복

## 전체 워크플로우 *(mandatory)*

```
[1] 관리자 → 법제처 API 동기화 실행
        ↓
[2] 시스템 → law_changes에 변경 기록 저장 (감지 로그)
        ↓
[3] 시스템 → 검토대상 조례 자동 판별 → revision_status = "검토대기" (빨간불 ON)
        ↓
[4] 부서 담당자 → 빨간불 조례 상세 열람 → revision_status = "검토중" (자동 전환)
        ↓
[5] 부서 담당자 → 법령↔조례 비교 후 검토의견 작성 (개정필요 or 개정불필요)
        ↓
[6] 관리자 → 검토의견 승인/반려
        ↓
[7] 시스템 → 승인 결과에 따라 조례 상태 자동 처리
```

### 승인 후 데이터 처리 규칙

| 검토의견 결과 | 관리자 판단 | ordinances.revision_status | 빨간불 | 비고 |
|--------------|------------|---------------------------|--------|------|
| 개정필요 | 승인 | "개정확정" | 유지 | 실제 조례 개정 완료 후 관리자가 수동 해제 |
| 개정불필요 | 승인 | null (정상) | 해제 | 검토 완료 처리 |
| (무관) | 반려 | "검토대기" | 유지 | 부서에 재검토 요청 |

### 조례 revision_status 생명주기

```
null (정상)
  ↓ [동기화 → 검토대상 판별]
"검토대기" (빨간불 ON)
  ↓ [부서 담당자 조례 상세 열람 → 자동 전환]
"검토중" (빨간불 유지)
  ↓ [담당자 검토의견 작성 + 관리자 승인]
  ├─ 개정필요 승인   → "개정확정" (빨간불 유지)
  │                     ↓ [조례 개정 완료 → 관리자 수동 해제]
  │                   null (정상, 빨간불 OFF)
  ├─ 개정불필요 승인  → null (정상, 빨간불 OFF)
  └─ 반려            → "검토대기" (빨간불 유지, 재검토)
```

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 법령 변경사항 목록 조회 및 필터링 (Priority: P1)

관리자가 동기화 후 감지된 법령 변경 기록을 다양한 조건으로 조회하여 전체 현황을 파악할 수 있다.

**Why this priority**: 변경 감지 기록을 확인할 수 없으면 어떤 법령이 변경되었는지 파악 자체가 불가능하다.

**Independent Test**: 법령 변경 데이터가 존재하는 상태에서 목록 페이지에 접근하여 필터링/검색이 정상 동작하는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 법령 변경사항이 존재할 때, **When** 관리자가 변경이력 목록에 접근하면, **Then** 전체 변경 기록이 페이지네이션과 함께 표시된다
2. **Given** 변경사항 목록이 표시된 상태에서, **When** API 응답 상태(성공/미응답/미발견), 소관부처, 동기화 일자, 개정유형으로 필터링하면, **Then** 조건에 맞는 변경 기록만 표시된다
3. **Given** 변경사항 목록이 표시된 상태에서, **When** 법령명으로 검색하면, **Then** 해당 키워드가 포함된 변경 기록만 표시된다

---

### User Story 2 - 변경사항 상세 조회 (Priority: P1)

관리자가 개별 법령 변경 기록의 상세 정보(변경 전/후 값, 소관부처, 동기화 정보)를 확인할 수 있다.

**Why this priority**: 상세 정보 없이는 변경의 실질적 내용을 파악할 수 없다.

**Independent Test**: 특정 변경 기록 클릭 시 상세 정보(변경 전/후 비교 포함)가 정확히 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 변경사항 목록이 표시된 상태에서, **When** 특정 변경 기록을 선택하면, **Then** 법령명, 변경 전 값, 변경 후 값, 소관부처, 동기화 일자, 동기화 배치, API 응답 상태가 표시된다
2. **Given** 변경 전/후 값이 존재할 때, **When** 상세 화면을 보면, **Then** 변경된 항목(법령명, 공포일, 시행일, 개정유형 등)이 비교 형태로 표시된다

---

### User Story 3 - 검토대상 조례 자동 플래깅 (Priority: P1)

동기화 후 시스템이 검토대상 조례를 자동 판별하여 빨간불(revision_status = "검토대기")을 표시한다.

**Why this priority**: 빨간불이 없으면 부서 담당자가 어떤 조례를 검토해야 하는지 알 수 없다.

**Independent Test**: 동기화 실행 후 검토대상으로 판별된 조례에만 빨간불이 켜지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 동기화로 법령 변경이 감지되었을 때, **When** 해당 법령과 연계된 조례가 있으면, **Then** 해당 조례의 revision_status가 "검토대기"로 변경된다 (빨간불 ON)
2. **Given** 동기화로 법령 변경이 감지되었을 때, **When** 해당 법령과 연계된 조례가 없으면, **Then** 어떤 조례에도 빨간불이 표시되지 않는다
3. **Given** 이미 "개정확정" 또는 "검토중" 상태인 조례가 있을 때, **When** 동일 법령의 새 변경이 감지되면, **Then** 기존 상태를 유지한다 (중복 플래깅 방지)

---

### User Story 4 - 부서 담당자 조례 검토 및 의견 작성 (Priority: P1)

부서 담당자가 빨간불 조례를 열어 법령↔조례를 비교한 후, 검토의견(개정필요/개정불필요)을 작성한다.

**Why this priority**: 부서 담당자의 검토가 없으면 관리자가 승인할 대상이 없다.

**Independent Test**: 부서 담당자가 빨간불 조례를 열면 상태가 "검토중"으로 전환되고, 검토의견을 작성할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** revision_status가 "검토대기"인 조례가 있을 때, **When** 부서 담당자가 해당 조례 상세를 열람하면, **Then** revision_status가 "검토중"으로 자동 전환된다
2. **Given** "검토중" 상태의 조례에서, **When** 부서 담당자가 검토의견(개정필요 또는 개정불필요)과 의견 내용을 작성하여 제출하면, **Then** 검토의견이 저장되고 관리자 승인 대기 상태가 된다
3. **Given** 담당자가 검토의견을 작성한 후, **When** 관리자 승인 전에 수정하려고 하면, **Then** 본인이 작성한 검토의견을 수정할 수 있다

---

### User Story 5 - 관리자 검토의견 승인/반려 (Priority: P1)

관리자가 부서 담당자의 검토의견을 확인하고 승인 또는 반려하면, 조례 상태가 자동으로 처리된다.

**Why this priority**: 관리자 승인이 최종 의사결정이며, 승인 후 데이터 자동 처리가 핵심 비즈니스 로직이다.

**Independent Test**: 검토의견을 승인하면 결과에 따라 조례 상태가 올바르게 변경되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** "개정필요" 검토의견이 대기 중일 때, **When** 관리자가 승인하면, **Then** 조례 revision_status가 "개정확정"으로 변경된다 (빨간불 유지)
2. **Given** "개정불필요" 검토의견이 대기 중일 때, **When** 관리자가 승인하면, **Then** 조례 revision_status가 null로 초기화된다 (빨간불 해제)
3. **Given** 검토의견이 대기 중일 때, **When** 관리자가 반려하고 사유를 입력하면, **Then** 조례 revision_status가 "검토대기"로 원복된다 (부서 재검토)
4. **Given** "개정확정" 상태의 조례가 있을 때, **When** 관리자가 조례 개정 완료를 확인하고 수동으로 해제하면, **Then** revision_status가 null로 변경된다 (빨간불 OFF)

---

### User Story 6 - Excel 내보내기 (Priority: P2)

관리자가 현재 필터 조건에 맞는 법령 변경 기록을 Excel 파일로 내보낸다.

**Why this priority**: 보고서 제출, 외부 공유 등 업무 활용을 위한 부가 기능이다.

**Independent Test**: 필터 적용 후 내보내기 버튼 클릭 시 Excel 파일이 다운로드되고, 내용이 화면 목록과 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 필터가 적용된 변경 기록 목록이 있을 때, **When** 관리자가 Excel 내보내기를 실행하면, **Then** 현재 필터 조건에 맞는 전체 데이터가 Excel 파일로 다운로드된다
2. **Given** 내보내기된 Excel 파일을 열면, **Then** 법령명, 변경항목, 변경 전/후 값, 소관부처, 동기화 일자 등 주요 컬럼이 포함되어 있다

---

### User Story 7 - 변경이력 통계 조회 (Priority: P2)

관리자가 소관부처별/기간별 법령 변경 통계를 조회하여 전체 현황을 파악할 수 있다.

**Why this priority**: 전체 현황을 수치로 파악해야 업무 우선순위 판단이 가능하다.

**Independent Test**: 통계 화면에서 소관부처별 집계가 실제 데이터와 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 변경 기록 데이터가 존재할 때, **When** 통계를 조회하면, **Then** 소관부처별 변경 건수가 표시된다
2. **Given** 변경 기록 데이터가 존재할 때, **When** 통계를 조회하면, **Then** API 응답 상태별(성공/미응답/미발견) 건수가 표시된다

---

### User Story 8 - 특정 법령의 변경 이력 추적 (Priority: P3)

관리자가 특정 법령에 대한 전체 변경 이력을 시간순으로 조회한다.

**Why this priority**: 개별 법령의 이력 추적은 심층 분석이 필요할 때 사용하는 부가 기능이다.

**Independent Test**: 특정 법령의 이력 조회 시 모든 변경 기록이 시간순으로 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 특정 법령에 대한 변경 이력이 여러 건 있을 때, **When** 해당 법령의 이력을 조회하면, **Then** 모든 변경 기록이 최신순으로 표시된다
2. **Given** 전체 변경 이력 요약을 요청할 때, **When** 이력 요약을 조회하면, **Then** 법령별 총 변경 횟수와 최근 변경일이 표시된다

---

### User Story 9 - 동기화 배치 및 일자 관리 (Priority: P3)

관리자가 동기화 배치 정보와 일자 목록을 확인하여 특정 시점의 동기화 결과만 조회할 수 있다.

**Why this priority**: 동기화 이력 관리는 데이터 추적과 디버깅에 필요한 운영 기능이다.

**Independent Test**: 동기화 배치 목록 조회 및 특정 배치의 변경 기록 필터링이 동작하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 여러 차례 동기화가 수행되었을 때, **When** 동기화 배치 목록을 조회하면, **Then** 각 배치의 동기화 일시와 건수가 표시된다
2. **Given** 동기화 일자 목록이 표시될 때, **When** 특정 일자를 선택하면, **Then** 해당 일자에 감지된 변경 기록만 필터링된다

---

### Edge Cases

- 동기화 중 네트워크 오류가 발생하면? → 해당 법령은 API 응답 상태가 '미응답'으로 기록되고, 다음 동기화 시 재시도된다
- 동일 법령에 대해 같은 배치에서 중복 변경이 감지되면? → 동기화 배치 ID와 법령 ID 조합으로 중복을 방지한다
- 이미 "검토중"인 조례에 동일 법령의 새 변경이 감지되면? → 기존 상태를 유지하고, 새 변경 기록은 law_changes에 추가된다
- 필터 조건에 맞는 변경 기록이 0건이면? → 빈 목록과 안내 메시지를 표시한다
- 담당자가 조례를 열었지만 검토의견을 작성하지 않으면? → "검토중" 상태 유지, 관리자가 목록에서 확인 가능
- "개정확정" 상태에서 동일 법령이 또 변경되면? → "개정확정" 유지, 새 law_changes 기록만 추가

## Requirements *(mandatory)*

### Functional Requirements

**법령 변경 기록 관리 (law_changes)**
- **FR-001**: 시스템은 동기화 후 감지된 법령 변경 기록 목록을 페이지네이션하여 제공해야 한다
- **FR-002**: 시스템은 변경 기록을 API 응답 상태(성공/미응답/미발견), 소관부처, 동기화 일자, 검색어, 개정유형으로 필터링할 수 있어야 한다
- **FR-003**: 시스템은 각 변경 기록의 변경 전/후 값을 비교 형태로 표시해야 한다
- **FR-004**: 시스템은 동기화 시 변경 기록을 매번 신규 생성하되, 동일 배치 내 동일 법령 중복을 방지해야 한다
- **FR-005**: 시스템은 현재 필터 조건에 맞는 변경 기록을 Excel 파일로 내보낼 수 있어야 한다
- **FR-006**: 시스템은 소관부처별/API 응답 상태별 변경 통계를 제공해야 한다
- **FR-007**: 시스템은 특정 법령의 전체 변경 이력을 시간순으로 제공해야 한다
- **FR-008**: 시스템은 동기화 배치 목록과 동기화 일자 목록을 제공하여 특정 시점 필터링이 가능해야 한다

**조례 검토 상태 관리 (ordinances.revision_status)**
- **FR-009**: 동기화 후 시스템은 검토대상 조례를 자동 판별하여 revision_status를 "검토대기"로 설정해야 한다
- **FR-010**: 부서 담당자가 "검토대기" 상태의 조례 상세를 열람하면 revision_status가 "검토중"으로 자동 전환되어야 한다
- **FR-011**: 부서 담당자는 검토의견을 "개정필요" 또는 "개정불필요" 중 하나로 작성할 수 있어야 한다
- **FR-012**: "개정필요" 검토의견이 관리자에 의해 승인되면 revision_status가 "개정확정"으로 변경되어야 한다
- **FR-013**: "개정불필요" 검토의견이 관리자에 의해 승인되면 revision_status가 null(정상)로 초기화되어야 한다
- **FR-014**: 관리자가 검토의견을 반려하면 revision_status가 "검토대기"로 원복되어야 한다
- **FR-015**: 관리자는 "개정확정" 상태의 조례를 수동으로 정상 상태(빨간불 해제)로 변경할 수 있어야 한다

**권한 관리**
- **FR-016**: 관리자만 검토의견을 승인/반려할 수 있어야 한다
- **FR-017**: 부서 담당자는 본인 부서 소관 조례의 검토의견만 작성할 수 있어야 한다

### Key Entities

- **법령 변경 기록 (Law Change)**: 동기화 시 감지된 개별 변경 로그. 대상 법령, 변경 전/후 값, 동기화 일자, 동기화 배치 ID, API 응답 상태를 포함한다. 승인/반려 대상이 아닌 순수 기록이다
- **자치법규 (Ordinance)**: 조례/규칙. revision_status 필드로 검토 진행 상태를 관리한다 (null/검토대기/검토중/개정확정)
- **검토의견 (Ordinance Review)**: 부서 담당자가 작성하는 검토 결과. review_result(개정필요/개정불필요)와 approval_status(대기/승인/반려)를 포함한다
- **상위법령 (Law)**: 변경 감지 대상이 되는 법령
- **동기화 배치 (Sync Batch)**: 한 번의 동기화 실행 단위. 배치 ID로 동일 실행 시점의 변경 기록을 그룹핑한다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 관리자가 변경 기록 목록을 조회하고 필터링하는 데 3초 이내로 결과가 표시된다
- **SC-002**: 동기화 후 검토대상 조례에 빨간불이 100% 정확하게 부여된다
- **SC-003**: 부서 담당자가 조례 상세를 열면 1초 이내에 "검토중" 상태로 자동 전환된다
- **SC-004**: 검토의견 승인 후 조례 상태 변경이 100% 정확하게 처리된다 (개정필요→개정확정, 개정불필요→정상)
- **SC-005**: 필터 조건이 적용된 상태에서 내보내기한 Excel 파일의 데이터가 화면 표시 내용과 100% 일치한다
- **SC-006**: 관리자가 아닌 사용자가 검토의견 승인/반려 기능에 접근 시 100% 차단된다

## Assumptions

- 법령 변경 기록은 법제처 API(MOLEG) 동기화를 통해 자동 감지되며, 수동 생성은 지원하지 않는다
- law_changes는 동기화 감지 로그이며, 개별 승인/반려 워크플로우가 없다
- 검토의견의 결과는 개정필요/개정불필요 2가지만 존재한다 (보류 없음)
- "검토중" 전환은 부서 담당자가 조례 상세 열람 시 자동으로 발생한다
- 조례 개정 완료 후 빨간불 해제는 관리자가 수동으로 처리한다
- 동기화 시 law_changes 기록은 매번 신규 생성하며, 기존 기록을 업데이트하지 않는다
