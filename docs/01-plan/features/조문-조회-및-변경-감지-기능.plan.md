# Plan: 조문 조회 및 변경 감지 기능

**Feature ID**: article-tracking
**Created**: 2026-02-14
**Status**: Planning
**Priority**: High

---

## 1. Feature Overview

### 1.1 배경
현재 law-matcher 시스템은 상위법령과 자치법규 간의 연계를 관리하지만, **조문 단위**의 추적은 불가능합니다. 상위 법령의 특정 조문이 개정되었을 때, 해당 조문과 관련된 조례를 자동으로 파악하고 알림을 제공하는 기능이 필요합니다.

### 1.2 목표
- 상위 법령의 조문을 조회하고 관리할 수 있는 전용 탭 추가
- 조문 단위로 자치법규와의 연계 관계 관리
- 조문 변경 이력을 자동 감지하여 관련 조례 개정 검토 알림

### 1.3 기대 효과
- **정확도 향상**: 법령 전체가 아닌 조문 단위로 변경 감지
- **업무 효율**: 영향받는 조례를 정확하게 파악하여 불필요한 검토 감소
- **선제적 대응**: 조문 변경 즉시 알림으로 빠른 대응 가능

## 2. Business Goals

### 2.1 핵심 목표
1. **조문 단위 추적**: 법령-조문-조례 3단계 연계 관리
2. **변경 감지 자동화**: 정기적 동기화를 통한 조문 변경 자동 감지
3. **사용자 경험 개선**: 직관적인 UI로 조문 조회 및 연계 조례 확인

### 2.2 성공 지표 (KPI)
- 조문 단위 변경 감지 정확도: 95% 이상
- 조문 조회 응답 속도: 2초 이내
- 사용자 만족도: 80% 이상 (설문 기준)

## 3. User Stories

### US-1: 조문 목록 조회
**As a** 법무 담당자
**I want to** 특정 상위법령의 조문 목록을 조회하고
**So that** 각 조문의 내용과 연계된 조례를 파악할 수 있다

**Acceptance Criteria:**
- [ ] 상위법령 선택 시 해당 법령의 전체 조문 목록 표시
- [ ] 조문번호, 조문제목, 조문내용 표시
- [ ] 각 조문별 연계된 조례 개수 표시

### US-2: 조문 상세 조회
**As a** 법무 담당자
**I want to** 특정 조문의 상세 정보를 조회하고
**So that** 해당 조문과 연계된 조례 목록을 확인할 수 있다

**Acceptance Criteria:**
- [ ] 조문 클릭 시 상세 페이지 이동
- [ ] 조문의 항, 호, 목까지 상세 표시
- [ ] 연계된 조례 목록 표시 (담당부서, 조례명)
- [ ] 조문 변경 이력 표시

### US-3: 조문-조례 연계 관리
**As a** 법무 담당자
**I want to** 조문과 조례의 연계 관계를 추가/수정/삭제하고
**So that** 정확한 영향 분석이 가능하다

**Acceptance Criteria:**
- [ ] 조문 상세 페이지에서 연계 조례 추가 버튼
- [ ] 조례 검색 및 선택 모달
- [ ] 연계 사유 또는 메모 입력 가능
- [ ] 연계 삭제 기능

### US-4: 조문 변경 감지 및 알림
**As a** 법무 담당자
**I want to** 상위법령 조문이 개정되면 자동으로 감지되고
**So that** 관련 조례의 개정 필요 여부를 빠르게 검토할 수 있다

**Acceptance Criteria:**
- [ ] 정기 동기화 (일 1회) 시 조문 변경 감지
- [ ] 변경된 조문 하이라이트 표시
- [ ] 영향받는 조례 자동 표시
- [ ] 개정법령 탭에 조문 변경 사항 추가

### US-5: 조문 변경 이력 조회
**As a** 법무 담당자
**I want to** 특정 조문의 변경 이력을 조회하고
**So that** 과거 변경 내역을 추적할 수 있다

**Acceptance Criteria:**
- [ ] 조문 상세 페이지에서 변경 이력 탭
- [ ] 공포일자, 변경 내용, 제개정 구분 표시
- [ ] 이전 버전과 현재 버전 비교 기능

## 5. Technical Considerations

### 5.1 법제처 API 활용

#### 조문 조회 API
- **Endpoint**: `http://www.law.go.kr/DRF/lawService.do`
- **Parameters**:
  - `OC`: API Key
  - `target`: "law"
  - `MST`: 법령 MST (고유번호)
  - `type`: "JSON"
- **Response**: 법령 상세 정보 (조문 포함)

#### 조문 변경 감지 전략
1. **방법 1**: 법령 이력 API 활용
   - Endpoint: `/DRF/lawHistService.do`
   - 장점: 변경 이력 직접 조회 가능
   - 단점: 조문 단위 변경은 직접 비교 필요

2. **방법 2**: 조문 내용 해시 비교
   - 조문 내용의 SHA-256 해시 저장
   - 동기화 시 해시 비교로 변경 감지
   - 장점: 빠른 비교, 정확한 감지
   - 단점: 추가 저장 공간 필요

**권장 방법**: 방법 2 (해시 비교) + 방법 1 (이력 조회)의 조합

### 5.3 Database Schema

```sql
-- articles 테이블
CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    law_id INTEGER NOT NULL REFERENCES laws(id) ON DELETE CASCADE,
    article_no VARCHAR(50) NOT NULL,
    article_title VARCHAR(500),
    article_content TEXT NOT NULL,
    paragraphs JSONB,  -- 항, 호, 목 구조
    content_hash VARCHAR(64),  -- SHA-256 해시
    last_synced_at TIMESTAMP,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    UNIQUE(law_id, article_no)
);

-- ordinance_article_mappings 테이블
CREATE TABLE ordinance_article_mappings (
    id SERIAL PRIMARY KEY,
    ordinance_id INTEGER NOT NULL REFERENCES ordinances(id) ON DELETE CASCADE,
    article_id INTEGER NOT NULL REFERENCES articles(id) ON DELETE CASCADE,
    mapping_reason TEXT,
    created_by INTEGER REFERENCES users(id),
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    UNIQUE(ordinance_id, article_id)
);

-- article_changes 테이블
CREATE TABLE article_changes (
    id SERIAL PRIMARY KEY,
    article_id INTEGER NOT NULL REFERENCES articles(id) ON DELETE CASCADE,
    change_date DATE NOT NULL,
    change_type VARCHAR(20) NOT NULL,  -- 'created', 'updated', 'deleted'
    old_content TEXT,
    new_content TEXT,
    old_hash VARCHAR(64),
    new_hash VARCHAR(64),
    detected_at TIMESTAMP DEFAULT NOW()
);

-- 인덱스
CREATE INDEX idx_articles_law_id ON articles(law_id);
CREATE INDEX idx_articles_content_hash ON articles(content_hash);
CREATE INDEX idx_ordinance_article_mappings_ordinance_id ON ordinance_article_mappings(ordinance_id);
CREATE INDEX idx_ordinance_article_mappings_article_id ON ordinance_article_mappings(article_id);
CREATE INDEX idx_article_changes_article_id ON article_changes(article_id);
CREATE INDEX idx_article_changes_change_date ON article_changes(change_date);
```

## 9. Risks and Mitigation

### Risk 1: 법제처 API 응답 지연
- **Probability**: Medium
- **Impact**: High
- **Mitigation**:
  - 타임아웃 설정 (30초)
  - 백그라운드 동기화 (사용자 대기 없음)
  - 캐싱 전략 (Redis)

### Risk 2: 조문 수가 많아 동기화 시간 초과
- **Probability**: High
- **Impact**: Medium
- **Mitigation**:
  - 법령별 순차 처리
  - Rate limiting (0.3초 간격)
  - 중단/재개 기능

### Risk 3: 조문 형식 변경 시 파싱 오류
- **Probability**: Low
- **Impact**: High
- **Mitigation**:
  - 예외 처리 및 로깅
  - 수동 확인 알림
  - Fallback to raw content
